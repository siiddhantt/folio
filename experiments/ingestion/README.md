# Local ingestion comparison

This experiment compares Docling 2.148.0 and LiteParse 2.18.0 on small synthetic
documents. It measures extraction and records inspectable evidence; it is not
Folio's application ingestion implementation or a general parser leaderboard.

Use Python 3.12 and a running Docker Linux daemon with amd64 support. Generating
fixtures also requires `reportlab`, `pypdf`, `python-docx`, and Poppler's
`pdftoppm` executable on PATH (or pass its path with `--pdftoppm`). Install those
Python packages in an isolated environment. The fixture generator writes input
files, reference answers, and visual previews to separate directories; only
the input directory is mounted into parser containers.

From the repository root:

```sh
python -m pip install reportlab pypdf python-docx
python experiments/ingestion/make_fixtures.py --output .local/ingestion-fixtures
docker build --platform linux/amd64 -t folio-liteparse:2.18.0 experiments/ingestion/liteparse
docker build --platform linux/amd64 -t folio-docling:2.148.0 experiments/ingestion/docling
python experiments/ingestion/run_comparison.py --fixtures .local/ingestion-fixtures/fixtures --results .local/ingestion-comparison-01
```

Builds download dependencies and model/language assets. The coordinator uses
already-built images, runs them sequentially, disables network access, mounts
fixtures read-only, and allows each container four CPUs and 6 GiB memory with no
additional swap allowance. It reads no `.env` file and calls no cloud service.
Use a new results directory for each comparison; earlier selected-parser outputs
are rejected rather than overwritten. To measure only one parser:

```sh
python experiments/ingestion/run_comparison.py --fixtures .local/ingestion-fixtures/fixtures --results .local/ingestion-liteparse-02 --parsers liteparse
```

`--liteparse-image` and `--docling-image` can select another already-built image
tag or image ID. Both adapters process the same sorted PDF/DOCX filenames and
make three consecutive attempts per file. Neither consumes reference answers.
Parser files under `liteparse/` and `docling/` retain raw results, normalized
source locations, diagnostics, timing, versions, and configuration. Inspect the
actual tables and page evidence against the separate reference files/previews;
successful parser return does not establish extraction completeness.

`coordinator/<parser>/container.json` records the image ID/digests, container
identity, limits, exit/OOM state, elapsed wall time, and container memory peak.
The adjacent `stdout.log` and `stderr.log` preserve Docker logs. A wrapper reads
the container's cgroup-v1 `memory.max_usage_in_bytes`, or cgroup-v2 `memory.peak`,
after the parser exits and preserves its exit code. That peak covers the whole
container, including native code and child processes; it is not a per-document
peak and may include charged cache. The wrapper cannot record it after an OOM
kill or forced termination; missing measurements remain unknown, not zero.

Each container has a 600-second deadline. On timeout the coordinator stops only
its uniquely named container, then preserves available logs and state. Containers
are deliberately retained for inspection; their names are in `container.json`.
Remove an inspected container with `docker rm <recorded-container-name>` when its
evidence is no longer needed. A nonzero coordinator exit signals a container,
timeout, or capture failure; inspect parser outputs separately for document-level
failures even when the container exits zero.

Timing excludes downloads and separates startup from conversion. The first file
and each newly initialized format can include lazy initialization; subsequent
same-process repeats are warmer. There is no OS-cache eviction. Compare individual
warmed repeats and compatible medians, not a single cold measurement. Docling
currently uses one compute thread; LiteParse allows two OCR workers and two OpenMP
threads. Equal container ceilings do not make these thread policies identical.
LiteParse uses Debian English OCR data and records its checksum; Docling records
its Tesseract/model configuration. These are configuration comparisons, not
isolated engine-speed claims.

The six fixtures exercise native text, scans, mixed pages, tables, damaged content,
and DOCX. They are useful for finding failure modes, but are too small to establish
production throughput or accuracy. DOCX pagination can be generated by conversion;
do not describe those positions as physical pages in the source Word document.
Retain image identities and environment/model manifests with any reported result:
the adapters have different dependency-pinning strengths, and an image tag alone
does not guarantee an identical rebuild.
